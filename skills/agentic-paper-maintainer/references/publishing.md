# GitHub、Pages 与 Release

仅在用户请求发布/同步的范围内执行。该仓库已有公开分享用途；不因每次增补公开论文而重复索取同一授权。新增私人笔记、未发表研究或别的仓库不自动包含在原授权中。发布不能以 skill 为由跳过平台要求的授权。

## 准备可发布内容

1. 查看 `git status`、当前分支、remote、最近提交及远端状态。保留用户已有改动，只提交本任务明确涉及的文件；不要使用清空工作区、强推或批量覆盖来解决分歧。
2. 先完成论文、导读、README 和网站改动，再运行构建及校验。检查公开差异不含密钥、下载错误页、个人环境文件和临时提取文本。
3. 区分普通内容同步与版本发布。用户只要求 Pages 更新时，正常提交推送即可，不必人为创建 Release；要求“更新 release page”时更新站点版本页，要求新 GitHub Release 或完整版本发布时也创建对应标签和 Release。上下文明确要求两者时一次完成。
4. 正式版本默认：小修正递增 patch，新增一批论文或阅读能力递增 minor；用户指定版本优先。先检查已有 tags / Releases，再选择未占用版本。已发布标签保持不变，后续更正通过新提交/版本完成。

## 版本一致性

同步 `scripts/build_site.py` 中版本、日期、首页标识、描述及 `release()` 文案，README 当前入口，以及 CHANGELOG 的新增记录。发布页写本轮新增/更新/更正、实际分类数量和重要边界；保留历史 CHANGELOG，不把每轮都称为“首个版本”。

日期使用用户当前时区。不要将库维护日期改成全部论文的核验日期。网站当前若用统一“资料核验”文案，应确保它不把未重审条目表述为已复核。

核对生成结果中的 `catalog.json`、`release.html` 和 canonical URL。默认项目站点路径包含 `/AgenticPaper/`，账号名以 remote 为准；不能只拼成域名根路径。

## 本地预览

沿用项目文档的 Python HTTP 预览，检查本次新增或修改的详情、PDF 链接及分类筛选；修改布局/交互时检查对应桌面与窄屏显示。不要每轮重新测试未变更的所有 UI。停止本任务启动的预览进程，保留用户已有服务。无法浏览器验证时明确报告已经做过的静态检查，不能声称完成视觉验证。

## 推送和自动部署

使用可用的 GitHub connector 或已配置的 `gh` / git；没有 CLI 登录时可用已登录浏览器完成 Release 操作，不读取或导出浏览器凭据。第一次执行先核对工具可用性，不假设上一轮的会话仍有效。

- 提交前查看 staged diff；shell 中多行说明写文件，通过 `--body-file` 等读取，不将论文文本拼成可执行 shell。
- 正常 push 本次分支；当前工作流在 `main` push 时部署、PR 只检查。不要绕过分支保护；若只能走 PR，完成 PR 并明确网站尚未部署。
- 检查对应提交的 Actions run 与 Pages deployment，而非仅看历史绿色勾。失败时定位 build、validation 或 deploy 层，修复任务内问题；认证/权限受阻时保留已完成的本地结果并报告具体阻塞，不能无界重试。

## 正式 Release

需要新版本时，在最终已校验提交创建新 annotated tag 并推送，再创建 GitHub Release。确认没有被占用的标签或同名 Release；网络重试前查询是否已成功，避免重复创建。

Release 说明至少包含版本、实际变更、正确的网站/版本页链接，以及影响阅读判断的更正。具体引用条数、论文数量从当前内容计算，不复用首次发布的 35 / 103。无需上传重复的全部 PDF 资产，除非用户要求独立离线包。

## 上线验收

- 对应提交的 workflow 和 deployment 成功。
- 正式主页、`release.html`、目录数据可访问且数量/版本一致。
- 抽查本轮修改的详情页和 PDF，核对内容或哈希，必要时检查页码锚点。
- 需要 GitHub Release 时确认已发布、链接正确、tag 指向最终发布提交；不要仅创建草稿便声称完成。
- 检查本地/远端提交关系和剩余工作区改动，区分用户原有改动与本次未完成工作。

如部署延迟或失败，交付可访问的仓库/版本链接和实际状态，不能将构建成功、推送成功与网站上线混为一谈。
